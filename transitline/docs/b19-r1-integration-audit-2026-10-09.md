# B19-R1 B19 저장·복원·stale·팩 혼입 통합 감사

기준은 master `cc32ecb`(B19-E1~E5, M1~M4 포함). **프로덕션 코드는 바꾸지 않았다.** 감사 결과는 `engine/test/b19-integration-audit.test.mjs`(10개 + todo 1개)에 실행 가능한 형태로 고정했고, 아래는 그 요약과 발견 사항이다. 실제 `ScenarioRuntime`과 실제 M1 예제 geometry로, 사슬 전체(E1 생애주기 → E3 철도 분담금 → E4 승인 기록 → E5 명시 수요 원천)를 한 스크립트(25단계)로 돌렸다.

## 발견 사항

### F-1 저장 바이트의 키 순서가 상태의 이력에 따라 달라진다 (중간, B20-R1에서 다룰 것)

`snapshotOperationalState`는 상태 객체의 키 삽입 순서를 그대로 내보내고 `restoreOperationalState`는 `stations`/`demandNodes`를 맨 뒤에 붙여 새로 만든다. 그래서 **로드 뒤에 처음 생기는 키**(예: E5의 `newTownExplicitDemandSources`, B15 적용 기록 등)는 로드를 거치지 않은 실행과 다른 자리에 놓인다. 내용은 같고 키 순서만 다르다. 같은 이력은 항상 같은 바이트이므로 지금 깨지는 기능은 없지만, B20의 "30년 저장 전후 바이트 결정성"은 이것에 걸린다. 해결은 저장 쪽에서 키를 정렬해 내보내는 것이 가장 작다(`integrated-save.mjs`, 이 작업의 소유가 아니라서 고치지 않았다). 이 테스트는 키를 정렬해 비교하고, 같은 이력의 원본 바이트 일치는 따로 검사한다.

### F-3 시나리오 팩 검사가 E5에만 있다 (높음: 돈이 걸린 경로)

E1·E3·E4는 넘겨받은 geometry의 `sourcePackId`를 기록하고 서로 일관성만 본다. 시나리오의 팩과 비교하는 곳은 E5뿐이다. 그래서 **다른 팩에서 그린 개발**에 대해 초안 → 합의 → 분담금 제안·합의·입금 확인 → **release(원장에 입금)**까지 막힘 없이 간다(`b19-integration-audit.test.mjs`의 todo 테스트가 이 흐름을 그대로 재현한다: 현금이 그 금액만큼 늘어남). 실제 게임에서는 지도 편집기가 시나리오 팩에서 export를 만들기 때문에 호스트가 잘못 연결했을 때만 생기지만, 돈이 움직이는 단계이므로 방어가 있어야 한다. 제안: `ScenarioRuntime`의 `proposeNewTownDevelopment`와 `releaseNewTownRailContribution`(필요하면 E3 propose·fund)에서 기록·geometry의 `sourcePack.packId`가 `pack.manifest.id`와 다르면 거절. 기존 E1/E3 런타임 테스트가 서로 다른 팩 id(`example-radial` geometry, 다른 런타임 팩)를 쓰므로 그 테스트들의 팩 id를 맞추는 작업이 같이 필요하다. 소유자 판단을 위해 todo로 남겼다.

### F-2 (확인된 정책, 결함 아님) 승인 뒤 E1 이력이 늘면 모든 승인이 stale이다

다른 단계의 입주 기록만으로도 같은 개발의 승인·수요 원천이 stale이 되고, 지연 → 재개처럼 상태가 돌아와도 이력이 늘었으므로 stale이다. E4 문서에 적힌 보수적 선택이며 감사에서는 일관성만 확인했다(E4·E5가 같은 사유를 낸다).

## 하지 않은 것

- 프로덕션 코드 수정 없음 (`management/**`, `scenario-runtime.mjs`, `integrated-save.mjs`, `main.mjs`, `index.html`, `style.css`, `map/**`).
- UI(M5/M6) 감사는 범위 밖이다. M5·M6의 mount가 이 보고서들만 읽는다는 것은 각 패널의 테스트가 다룬다.
