- 상위 설계: [철도 종합보고서](railway-construction-master-report-kr-jp-2026.md), [사업수주·경제성·경쟁회사 보고서](transport-business-award-economics-competition-kr-jp-2026.md)

## 0. 결론 — 무엇부터 할 것인가

지금은 설계 문서가 충분히 쌓였지만 실제 코드는 기존 Phase 1 운행 엔진 수준이다. 현재 엔진에는 돈·건설·보유차량·차량기지·사업입찰·저장이 없고, 시간·열차·승객 처리에 먼저 고쳐야 할 문제가 남아 있다.

따라서 실제 순서는 다음으로 고정한다.

```text
I0 기존 엔진 안정화
→ I1 공통 상태·명령·시간·회계·저장 기반
→ I2 수요지점·역·선로·운행노선 분리와 지도 데이터 계약
→ I3 첫 수주 게임: 공공소유 철도 O&M 입찰
→ I4 기본 철도 건설: 계획·견적·공사·개통
→ I5 차량 발주·편성·차량기지·개통준비
→ I6 승객·배차·운임·운영비·KPI 경영 사이클
→ I7 사업수주·금융·경쟁회사와 공학 깊이 확장
→ I8 한국·일본 프로필·지도 통합·장기 부하 검증
```

처음부터 일본 철도사업 전체, 한국 민자사업 전체, 모든 주행 시스템을 동시에 만들지 않는다. 아래 두 개의 수직 완성본을 먼저 통과한다.

### 첫 번째 완성본 A — 운영권 수주

```text
공공이 보유한 가상 철도 노선
→ 플레이어가 사업을 조사
→ Bid/No-Bid
→ 가상 경쟁사와 O&M 입찰
→ 우선협상·계약
→ 차량·인력·기지 사용권 준비
→ 30일 운영
→ 서비스대가·KPI 감액·영업손익
→ 저장·복원
```

### 두 번째 완성본 B — 건설부터 개통

```text
중형 철제차륜, 복선, 지상·단순고가
→ 역 3~5개와 선로 계획
→ 비용·기간·호환성 견적
→ 착공·공정·지출
→ 차량 발주·D1 차량기지 확보
→ 통합시험·OpenReady
→ 개통·운행·수입·유지비
→ 재투자
```

완성본 B까지 통과하면 이 게임의 핵심인 `사업 확보 → 건설 → 차량·기지 → 개통 → 운영 → 돈 → 재투자`가 처음으로 연결된다.

## 1. 현재 위치

### 1.1 완료된 것

- 게임 역할과 범위 확정: 플레이어는 버스·철도 교통회사 대표.
- 도로·도시는 유지하고 버스·철도망만 설계한다는 경계 확정.
- 기존망 유지/초기화, 자금 제한, 샌드박스/시나리오 설정 구조 확정.
- 철도 규격·역·공사·차량·제작사·차량기지의 여섯 시스템 설계 완료.
- 한국·일본 사업절차, 비용·기간·지연, 차량기지 갈등과 입지 설계 완료.
- 사업수주, B/C·NPV·IRR·DSCR·VFM, 경쟁회사와 입찰자 수 설계 완료.
- Claude가 담당한 지도·데이터 보안·정합성 항목 S-01·S-02·D-01~D-05 수정 완료 기록.
- 기존 엔진 테스트 3개가 2026-09-25 기준 통과:
  - `bathymetry.test.mjs`
  - `od-demand.test.mjs`
  - `spatial-index.test.mjs`

### 1.2 아직 구현되지 않은 것

- 건설 상태와 건설비.
- 회사 현금·원장·재무제표.
- 차량 모델·편성·실물 보유자산.
- 차량 발주·제작·납품.
- 차량기지와 정비용량.
- 사업기회·입찰·경쟁회사·계약.
- 저장·불러오기와 버전 변환.
- 한국·일본 국가 프로필.
- 현실 축척의 승객·정원·요금·운영비.

### 1.3 선행 수정이 필요한 엔진 문제

[코드 검토 문서](code-review-2026-09-22.md)의 E-01~E-07은 미착수 상태다.

| 번호 | 문제 | 뒤에 생기는 피해 |
|---|---|---|
| E-01 | 큰 시간 간격에서 열차 이동·정차가 프레임에 따라 달라짐 | 배속에 따라 수송량과 수입이 달라짐 |
| E-02 | 24시간 달력·다일 진행 오류 | 공기·급여·운임·이자가 잘못 계산됨 |
| E-03 | 중단 노선과 환승 경로 처리 | 없는 서비스로 승객과 수입이 계산됨 |
| E-04 | 대기·포기 시각 처리 | 대기시간과 만족도·수요가 왜곡됨 |
| E-05 | 노선 삭제·운행 중 승객 위치 | 승객 소실·잘못된 환불·통계 발생 |
| E-06 | 출발지=목적지 예외 | 한 수요가 전체 루프를 중단할 수 있음 |
| E-07 | 도쿄 규모 경로탐색 비용 | 배속·대규모 수요에서 메인 스레드 병목 |

경제 시스템은 시간과 승객 수송 결과에 돈을 곱하는 계층이므로 I0보다 먼저 구현하지 않는다.

## 3. I0 — 기존 엔진 안정화

### 목적

건설·경제 계산이 의존할 시간, 이동, 경로, 승객 결과를 신뢰할 수 있게 만든다.

### 작업 순서

1. `package.json`에 전체 엔진 테스트를 한 번에 실행하는 명령을 추가한다.
2. E-01~E-06의 재현 사례를 영구 테스트로 먼저 작성한다.
3. 고정 간격 시뮬레이션과 렌더 프레임을 분리한다.
4. 한 틱에서 남은 시간을 소비하며 여러 구간·정차 사건을 처리하도록 열차 이동을 수정한다.
5. 날짜를 24시간 기준으로 계산하고 심야 영업일을 별도 규칙으로 둔다.
6. 운행 중단·노선 삭제·환승·승객 포기·동일지점 이동을 수정한다.
7. 네트워크 버전별 경로 캐시와 우선순위 큐 또는 출발지별 재사용을 구현한다.
8. 1x·2x·4x와 불규칙 렌더 프레임 비교 테스트를 추가한다.

### 건드릴 가능성이 높은 현재 파일

- `engine/src/loop.mjs`
- `engine/src/trains.mjs`
- `engine/src/state.mjs`
- `engine/src/routing.mjs`
- `engine/src/passengers.mjs`
- `engine/src/mode-choice.mjs`
- `engine/src/network.mjs`
- `engine/test/`

### 완료 관문 I0

- 기존 3개 테스트와 신규 E-01~E-07 테스트가 한 명령으로 통과한다.
- 같은 명령·난수·시뮬레이션 시간을 1x·2x·4x로 실행해 핵심 상태가 같다.
- 열차가 큰 틱에서 역이나 종착 회차를 건너뛰지 않는다.
- 7일 실행 뒤 시간대와 영업일이 밀리지 않는다.
- 노선 삭제 뒤 승객이 삭제된 열차·노선에 남지 않는다.
- 도쿄 고정 그래프 경로탐색 벤치마크가 기록되고 기존 측정 대비 개선된다.

## 4. I1 — 공통 상태·명령·시간·회계·저장 커널

### 목적

각 기능이 직접 전역 상태를 수정하지 않고 검증 가능한 명령과 사건으로 움직이게 한다.

### 핵심 모듈

```text
SimulationClock
  시뮬레이션 시각, 영업일, 배속, 예약 사건

DeterministicRng
  고정 시드, 난수 상태 저장, 사건 재현

CommandHandler
  명령 검증 → 하나의 거래로 상태 변경 → 결과 반환

EventLog
  공사·계약·차량·운영 사건의 원인과 결과 기록

Ledger
  계정, 거래, 미지급·확정의무, 잔액 검증

SaveGame
  schemaVersion, packVersion, rngState, clock, domainState
```

### 첫 회계 범위

- 초기 출자금.
- 제안 준비비.
- 입찰보증 한도.
- 건설 계약금·기성금.
- 차량 계약금·납품금.
- 운임·공공 서비스대가.
- 인건비·전력·정비·시설사용료.
- KPI 보너스·감액.

처음부터 세무회계 전체를 만들지 않는다. 모든 현금 변동에 근거 거래가 있고 잔액을 재구성할 수 있는 것이 첫 목표다.

### 완료 관문 I1

- 실패한 명령이 상태 일부와 돈 일부만 바꾸지 않는다.
- `기초현금 + 현금유입 - 현금유출 = 기말현금`이 항상 성립한다.
- 같은 저장본·명령·시드에서 같은 사건과 결과가 나온다.
- 저장 후 복원한 실행과 중단 없이 실행한 상태가 같다.
- 저장 형식에 버전이 있으며 알 수 없는 미래 버전은 명시적으로 거절한다.

## 5. I2 — 수요·시설·서비스 분리와 데이터 계약

### 목적

현재 `demand point = station` 구조를 없애 자유로운 역 건설과 기존망·외부망을 받을 수 있게 한다.

### 내부 객체

```text
DemandNode        인구·일자리·OD·특수수요
AccessLink        수요지점↔역, 역↔역의 보행시간·접근성
Station           실제 건설·소유·운영되는 역
PlatformEdge      승강장 가장자리와 수용 편성
TrackSegment      물리 선로와 구조·규격·상태
ServiceLine       정차역·운행계통·목표배차
VehicleUnit       실제 보유한 편성
ExternalNetwork   플레이어가 소유하지 않는 기존 교통망
```

### Claude와 맞출 입력 계약

지도 쪽은 다음처럼 정규화된 계획 입력만 넘긴다.

```text
PlanGeometry
  planId
  coordinateReference
  stationCandidates[]
  segments[]
    lengthMeters
    elevationStartMeters
    elevationEndMeters
    structureHint
    constraintFlags[]
    dataQuality
  accessLinks[]
  sourcePackId
  sourcePackVersion
```

우리 엔진은 다음을 반환한다.

```text
PlanAssessment
  buildable: true | false | conditional | unknown
  violations[]
  missingInputs[]
  estimateRange
  durationRange
  technicalProfileCompatibility
```

지도 쪽이 선을 그렸다고 건설 가능으로 간주하지 않는다. 필수 자료가 없으면 `unknown` 또는 `conditional`로 반환한다.

### 호환 전략

- 기존 CityPack 수요점은 어댑터에서 `DemandNode`로 변환한다.
- 현재 기존 노선은 `ExternalNetwork` 또는 명시적 시작자산으로 변환한다.
- 현재 Phase 1 UI가 새 도메인 객체를 직접 알 필요가 없도록 조회 어댑터를 둔다.
- 데이터 생성 스크립트는 런타임 엔진 안으로 옮기지 않는다.

### 완료 관문 I2

- 수요지점에 역이 없어도 엔진이 실행된다.
- 한 수요지점이 여러 역에 서로 다른 보행시간으로 연결될 수 있다.
- 선로와 운행노선을 따로 삭제·중지·조회할 수 있다.
- 합성 데이터로 PlanGeometry 입력 검증과 결측 처리 테스트가 통과한다.
- 기존 예제팩과 도쿄팩을 어댑터로 계속 읽을 수 있다.

## 6. I3 — 첫 수주 게임, 완성본 A

### 목적

건설보다 작은 범위에서 회사·경쟁·입찰·계약·운영경제의 재미를 먼저 검증한다.

### 기준 시나리오

```text
국가: 일본형 가상 도시
사업: 공공소유 중형 철도 O&M 운영권
노선: 기존 완공 5개 역
계약: 20년, 고정 서비스대가 + KPI 보너스·감액
경쟁회사: 지속 객체 5개
예상 실제 입찰: 2~4개
플레이어 선택: 요구 운영대가, 배차, 인력, 예비차, 품질계획
```

### 구현 범위

- `BusinessOpportunity`와 공고·마감일.

- 경쟁사별 적격성·참가 여부·비공개 제안.
- 적격→최소기술→종합점수 3단계 평가.
- 무응찰·단독응찰·탈락·우선협상·차순위 전환.
- 단순 계약과 KPI 지급·감액.
- 입찰·계약·30일 운영 상태 저장.

### 이번 단계에서 제외

- 대형 건설 PPP.
- 실제 회사명.
- 복잡한 대출·세금·자금재조달.
- 컨소시엄 내 수십 개 계약.
- 인수합병과 파산.

### 완료 관문 I3

- 경쟁사 수가 고정값이 아니라 적격성과 Bid/No-Bid로 0~5개 사이에서 결정된다.
- 최저가라도 최소기술을 못 넘으면 탈락한다.
- 우선협상 결렬 시 차순위자 또는 재공고로 간다.
- 낙찰 뒤 30일 운영에서 서비스대가·비용·KPI 감액이 원장에 기록된다.
- 낮은 가격으로 이겨도 실제 운영손실이 날 수 있다.

## 7. I4 — 기본 철도 건설

### 목적

선을 그으면 즉시 완성되는 현재 구조를 계획·공사·자산 상태로 바꾼다.

### 첫 지원 범위

- 일반 철제차륜 중형.
- 복선.
- 지상과 단순 고가.
- 일반역 3~5개.
- 상대식·섬식 승강장.
- 단순 종착 회차.
- 토지보상은 외부입력 또는 제외 사유로 별도 표시.

### 구현 객체

```text
TechnicalProfile
StationPlan
TrackPlan
ConstructionEstimate
ConstructionPackage
ConstructionContract
ConstructionTask
InfrastructureAsset
```

### 상태

```text
draft
→ estimated
→ approved
→ tendering
→ contracted
→ underConstruction
→ inspection
→ available

분기: revised / suspended / cancelled / failed
```

### 구현 규칙

- 구조물 경로 km와 선로 km를 분리한다.
- 직접공사비·설계관리·통합시험·예비비를 분리한다.
- 비용은 계약·기성 사건에 따라 지급한다.
- 공구와 작업팀이 실제 개월을 소비한다.
- 미개통 시설은 열차·승객 경로에 들어가지 않는다.
- 취소·변경 시 이미 수행된 공사는 전액 환불되지 않는다.
- 모든 견적은 기준값과 범위를 함께 반환한다.

### 완료 관문 I4

- 합성 입력으로 역 3~5개 노선을 견적→착공→완공할 수 있다.
- 돈이 부족하면 계약이나 기성 지급이 원자적으로 실패한다.
- 배속을 바꿔도 같은 게임 날짜에 같은 진척·지출이 발생한다.
- 저장·복원 뒤 공정과 계약잔액이 일치한다.
- 공사 중인 선로는 운행에 사용되지 않는다.

## 8. I5 — 차량·편성·제작사·차량기지

### 목적

본선만 완공했다고 개통되지 않게 한다.

### 차량 범위

- 중형 철제차륜 카탈로그 모델 1종.
- 4량 기본편성, 허용범위 내 증결 가능.
- 실제 편성별 납품일·거리·검사상태.
- 가상 제작사 3곳.
- 가격·납기·품질·보증·수주잔량 평가.
- 계약→설계준비→제작→공장검사→운송→인수→노선시험.

### 차량기지 범위

- D1 유치·일상검사기지 한 종류.
- 유치용량, 검사선 처리량, 입출고경로.
- 자체부지 또는 기존기지 사용계약.
- 종점 회송거리와 편성km 비용.
- 중정비는 외부계약으로 시작.

### 개통 판정

```text
OpenReady =
  trackAndStationsAvailable
  && minimumFleetAccepted
  && depotCapacitySecured
  && entryRouteAvailable
  && powerSignalIntegrated
  && staffAndTimetableReady
  && trialOperationPassed
  && approvalsAndContractsValid
```

### 완료 관문 I5

- 차량 발주가 늦으면 본선 완공 뒤에도 개통이 지연된다.
- 제작사 생산슬롯과 발주량에 따라 납품일이 달라진다.
- 차량·승강장·전력·신호 규격 불일치는 시험 전에 차단된다.
- 기지 수용량보다 많은 편성을 보유하면 운영준비 경고가 발생한다.
- 회송거리 변화가 운영비와 첫차·막차 준비에 반영된다.

## 9. I6 — 운영·승객·경제 완성본 B

### 목적

건설한 시설과 구입한 차량으로 실제 서비스를 운영하고 재투자 판단을 하게 한다.

### 구현 범위

- 왕복주기·목표배차로 필요한 편성 계산.
- 보유·운행·검사·예비·고장 편성 구분.
- 시간대별 배차와 실제 공급.
- 정원·만차 미탑승·대기·환승·도착.
- 간단 요금과 환승정산.
- 운임·광고·공공대가 수입.
- 인건비·전력·정비·회송·시설유지·사용료 지출.
- 일·월 손익, 현금흐름, 운임회수율.
- 정시율·혼잡·가용률·KPI.
- 현금부족 경고와 단순 운행축소.

### 첫 균형 원칙

- 현재 화면용 승객 1명을 현실 승객 1명으로 바로 계산하지 않는다.
- `passengerWeight` 또는 집단승객 축척을 모든 정원·운임·통계에 동일 적용한다.
- 요금은 한 여정 단위인지 승차 단위인지 먼저 고정한다.
- 유지비는 거리·시간·자산가치 중 어떤 기준인지 항목별로 명시한다.
- 화면 통계와 원장 수치는 같은 원시 사건에서 집계한다.

### 완료 관문 I6

- 3~5개 역 노선에서 사업 확보 또는 자체계획→건설→차량→기지→개통→30일 운영이 이어진다.
- 배차를 늘리면 대기시간은 줄고 차량·인력·전력비가 증가한다.
- 차량 부족 시 열차가 자동 생성되지 않는다.
- 흑자·적자의 원인을 수요·운임·비용·부채가 아니라 현재 지원 범위 안에서 설명할 수 있다.
- 배속·저장으로 운임과 비용이 중복 발생하지 않는다.
- 30일 후 승객·차량·원장·계약 불변식이 모두 유지된다.

이 시점이 첫 번째 실제 알파 완성선이다.

## 15. 진행 관리 규칙

- 문서 작성 완료와 코드 구현 완료를 구분한다.
- 테스트 없는 상태변경 기능은 완료로 표시하지 않는다.
- 실제자료, 게임 확정규칙, 임시 밸런스 값을 코드와 데이터에서도 구분한다.
- 금액은 정수 JPY 최소단위 또는 명시적 고정소수 표현을 사용한다.
- 모든 기간은 시뮬레이션 시계 하나를 사용한다.
- 지도 UI는 엔진 상태를 직접 변경하지 않고 명령을 보낸다.
- 결측 공간자료는 비용 0·건설 가능으로 바꾸지 않는다.
- 경쟁AI에게 플레이어와 다른 무한자금·즉시건설 특혜를 주지 않는다.
- 기존 팩·사용자 변경을 파괴하는 대규모 리팩터링을 한 번에 하지 않는다.
- 각 단계 종료 때 변경 파일, 테스트 명령, 결과, 남은 한계를 기록한다.

## 16. 최종 개발 판단

지금 바로 해야 할 것은 I0다. 철도 종류나 공사비 표를 더 늘리는 작업보다 기존 운행 엔진의 시간·경로·승객 결과를 먼저 신뢰할 수 있게 만들어야 한다.

I0 다음에는 추상적인 거대 경제 시스템을 한꺼번에 만들지 않고, I1~I3으로 작은 O&M 수주 게임을 완성한다. 그 뒤 I4~I6에서 건설·차량·기지·운영을 연결한다. 이 순서를 따르면 각 단계에서 플레이 가능한 결과가 생기고, 지도 작업을 기다리지 않고도 합성 시나리오로 검증할 수 있다.
