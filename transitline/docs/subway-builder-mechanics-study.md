# Subway Builder 메카닉 학습 + 우리 도쿄 지도 연계 계획 (2026-09-25)

> **읽은 대상:** 이 PC에 설치된 게임 v1.7.1(metro-maker4, Borough Studio)의 렌더러 번들 —
> `simEngine.worker`(열차/신호/경제 규칙)와 `popCommuteWorker`(수요/경로/수단 선택) — 와 `game-rules.json`,
> `strings.json`, 도시 데이터 폴더(TOK/OSA/NAG). asar는 프로젝트 밖 임시 폴더에 풀어서 **읽기만** 했고, 코드를 실행하거나
> 이 저장소로 복사하지 않았다. 상용 게임의 코드/에셋은 재사용 권한이 없다는 전제(참고 문서 §7~§12와 같은 기준)로,
> **동작·수치를 이해해서 우리 코드로 새로 쓴다.** 게임 EULA는 확인하지 않았다.
>
> **확인된 것과 아닌 것을 구분한다.** 아래 "확인"은 소스 텍스트에서 직접 읽은 값이다. 메인 프로세스(`main.jsc`)는
> V8 바이트코드라 읽을 수 없고, 렌더러 번들 안에도 난독화(`_0x…`) 구간이 있어 "미확인"으로 남겼다.

## 0. 먼저 풀어야 할 모순 (수치 출처)

코드 기본값(`RULES_SPEC`)과 번들된 `data/game-rules.json`이 서로 다르다.
**판단(근거 있음, 게임 내 실측은 아직)**: 실제 적용은 코드 기본값일 가능성이 높다. 근거 — ① 렌더러 4개 번들 어디에도 `game-rules` 문자열이 없고
메인 프로세스 바이트코드에도 없다(파일을 읽는 코드가 발견되지 않음). ② json 첫 줄이 `"$schema": "../../schemas/game-rules.schema.json"`이라
모딩용 예시/스키마 문서로 배포된 파일로 보인다. ③ 모딩 API `modifyConstants`가 코드의 `RULES`에 `deepMerge`로 덮어쓴다
(= 런타임 원본은 코드의 `RULES`). 남는 불확실성: 메인 프로세스(`main.jsc`)는 읽을 수 없어 거기서 읽는지는 배제 못 함.
**확정하려면 게임 안에서 값 하나(예: 최대 선로 길이 5,000 vs 10,000 m)로 확인.**

| 항목 | 코드 기본값 | game-rules.json |
|---|---|---|
| MAX_TRACK_LENGTH | 10,000 m | 5,000 m |
| AT_GRADE 공사비 배수 | 0.35 | 0.3 |
| MAX_ELEVATION | 20 m | 15 m |
| 환승 최대 횟수 | 4 | 3 |
| 도보 접근 최대 | 45분 | 30분 |
| 운전비/km | 0.65 | 0.6 |
| 채권 이자(일) | 6% / 4% / 2% | 10% / 8% / 6% |
| 표고 구간 | 7단계(TRENCHED/RAMP 포함) | 5단계 |

코드 쪽이 더 새 스키마(구간 추가, 주석에 v1.4 이후 변경 이력)라서 기본은 **코드 기본값을 채택**하되, 게임 UI에서 표본 확인 후 확정.

## 1. 확인된 메카닉

### 시간·시뮬레이션
- 고정 틱 = 게임 0.5초. 속도 4단계: 1x=1, 2x=25, 3x=250, 4x=500 게임초/실초. 하루 = 3x에서 약 5.8분.
- 수요 릴리스 간격 15분(`COMMUTE_INTERVAL_LENGTH`=900). 시간대 5단계 수요 배수: 0.15 / 0.3 / 0.8 / 1.0 / 2.5.
  시간대별 자동차 소요시간 배수: 0.8 / 0.9 / 1.0 / 1.25 / 1.5.
- 열차 편수는 수요 구간 전환 30분 전후로 부드럽게 증감(`TRAIN_SCHEDULE_TRANSITION_WINDOW`=1800, 최대 90분).
- 유지비 정산: 인프라 5분, 운영 15분마다. 채권 이자는 매 게임 시간 일이자의 1/24.

  트렌치·지표·램프는 사실상 불가=100).

## 2. 난독화 구간 해독 결과 (텍스트로만 읽음, 실행 없음)

난독화는 문자열을 회전 배열에서 꺼내 쓰는 방식이라, 함수 흐름은 그대로 읽히고 상수 이름만 가려져 있다. 배열 안 이름
(`INCOME_STD_DEV`, `PARKING_TIME` 등)과 코드 문맥을 맞춰서 복원했다. 배열 인덱스 하나하나를 실행으로 검증하지는 않았으므로
아래 "이름 복원"은 **문맥 추론**이다(산식 구조는 확실, 개별 상수 이름 매칭은 높은 확률).

### 수단 선택 (`getModeChoiceForPerson`, popCommuteWorker 30565행) — 사람 1명 단위, 결정론적
1. 소득 = 그 pop 안에서의 순번 i를 분위수 `i/(N−1)`로 보고 정규분포 역함수로 변환: `평균×배수 + z×표준편차`, 15k~200k로 자름.
   소득이 하한+5,000 이하이면 0.1~0.95 분위수로 다시 뽑고, 아니면 10%의 사람에게 최대 +$100k를 더한다.
   난수는 `i×362436069 mod 1e6`을 쓰는 해시라서 **같은 pop은 항상 같은 결과**(재현 가능).
2. 초당 시간가치 = 소득 / 1860시간 / 3600.
3. 세 가지 총비용(달러)을 각각 계산해서 **가장 싼 것을 선택**. 동률이면 자동차 > 대중교통 > 도보 순.
   - 자동차 = (체감 운전시간 × 시간가치 + 운전비) × 단거리 패널티. 운전비 = km × 0.65 + 주차비(공항 5배).
     단거리 패널티 = 1 km 미만이면 `1 + (1000 − 거리m)/1000`, 아니면 1.
   - 대중교통 = 체감 여행시간 × 시간가치 + 운임.
   - 도보 = 도보시간 × 시간가치.
4. 체감 운전시간 = `t × 시간대 배수 × (1 + 혼잡비율 × (1.33 − 1)) + 주차시간 180초 × 2 × 1.6`,
   혼잡비율 = `(배수−1)/(2−1)`을 0~1로 자른 값.
5. 한 수요 지점 안에서 대중교통 선택이 10명 미만이면 전원을 자동차로 돌린다(성능 최적화용 규칙).

### 체감시간 (`computePerceivedTime`)
경로의 각 구간(segment)을 합산: 차량 탑승 1.0배, 걷기 ×1.39, 운전 ×1.0(혼잡 프리미엄은 위 자동차 계산에만),
대기 = (첫 구간 출발 ~ 마지막 구간 도착) − 구간 시간 합 → ×1.37, 원하는 출발보다 늦게 떠나는 시간 ×0.4.

### 운임 (`computeJourneyFareBreakdown`, 30465행)
- 노선마다 `요금 그룹(groupId)`에 속하고, 그룹마다 `fareSystem`이 있다: **정액**, **노선별**(그 노선을 탈 때마다), **구역제**(기본 + 구역당),
  **거리제**(기본요금 + km당 요금, 상한 `fareCap`). 금액은 0.05 단위로 반올림.
- 거리제 거리는 **승차역~하차역 직선거리**. 그룹 안 환승 정책은 `count-within-group`(기본: 그룹 안에서는 누적거리로 한 번만 계산)과
  `all-paid`(구간마다 전액). 다른 그룹으로 갈아탈 때 이전 구간이 있으면 새 그룹의 기본요금을 **공제(credit)**할 수 있다.
  → 운영사별 요금 그룹 + 환승 공제라는 구조 자체가 일본식 다중 운영사 요금과 잘 맞는다(§6).
- `FARE_MULTIPLIER` = 1 × 365. 이름은 `TIME_FARE_MULTIPLIER`라서 "하루치 운임을 1년치로 환산"하는 시간 배수로 보이지만, **확정하지 못했다**
  (앞 문단의 "표본 인구 환산" 해석은 추측이었다).

### 열차 이동 (`updateTrainMotion`, simEngine 31661행) — 평문
틱 0.5초마다: 목표 속도와 차이가 0.01 미만이면 유지. 가속 시 증가분 = `min(최대가속×dt, 남은 속도차)`, 그리고 전 틱 증가분 대비
증가 폭이 `저크×dt²`를 넘지 못하게 자른다(저크 제한은 가속에만). 감속은 `max(−최대감속×dt, 속도차)`로 저크 제한 없이 즉시.
값은 소수 4자리로 반올림. 제동 거리는 이 루프를 반복(최대 1,000회)해서 구하고 결과를 캐시.

### 노선 구조·편수·스케줄 (simEngine 1565~1665, 31052~31205, 31407~31475행)
- **노선 = 정차역 목록(`stNodes`) + 역 사이 구간(`stCombos`)**. `stCombos[i]`는 i번째 정차역에서 다음 정차역까지 지나는 **선로 경로**
  (앞의 선로 2개가 승강장 트랙). 즉 `stCombos`는 급행 패턴이 아니라 "구간별 선로 경로"이며, 종착역에서 다른 승강장을 쓰는 예외는
  `stComboOverrides`/`allowedTerminusPlatforms`로 처리한다(문서 초판의 "급행 패턴" 해석은 **틀렸다**).
- **편수는 "동시에 달리는 열차 수"로 정한다**: 노선마다 `trainSchedule = {high, medium, low, veryLow}` = 수요 등급별 열차 대수.
  열차에 번호를 매겨 `번호 < 등급별 대수`인 열차만 그 등급에서 운행(높은 등급일수록 추가 열차가 투입되는 중첩 구조).
- **시간(정시) → 편수 등급** (열차용, 수요 배수용 11구간 표와는 별개):
  veryLow = 23~2시, low = 3~5시·20~22시, medium = 6시·10~15시·19시, high = 7~9시·16~18시.
- 등급이 바뀌는 정시 전후로 열차 대수를 **선형 보간**. 보간 폭은 `min(노선 왕복시간, 90분)`(왕복시간을 모르면 30분)이 양쪽으로 적용.
- **시간표 모드**(기능 플래그): `periods = [{startHour, endHour, headwaySeconds}]`로 간격을 직접 지정하면 대수 = `ceil(왕복시간 / 간격)`, 경계에서 같은 방식 보간.
- **열차 투입(spawn)**: 노선 위 기존 열차들을 진행률로 정렬해 **가장 큰 빈 구간의 중간 정차역**에 투입. 그 역에 열차가 있거나
  승강장 접근 신호 구간이 점유/예약돼 있으면 다음 후보, 전부 막히면 0번 역, 그것도 막히면 투입 안 함. 편성 길이(칸수×칸 길이)가
  노선의 어느 승강장 트랙 길이 합보다 길면 "Train too long"으로 투입 불가.
- **승강장 예약**(`PlatformReservations`): 열차가 다음 승강장을 미리 점유(claim). 다른 열차가 예약했으면 대기. 진입·출발 경로의 방향 코사인이
  −0.5 미만이면 정차 중 진행 방향이 바뀌는 것(회차/후진)으로 판정.

### 선로 배치 검증 (`index-*.js` 141092~141260행 외) — 그리기 중 실시간 검사
- 선로 1개: 길이 10 m ~ 10,000 m(+0.1), 점 2개 이상. 차량기지 선로는 별도 최소 길이.
- **역 트랙**: 길이가 `[최소 편성 길이, 최대 편성 길이 + 0.2 m]` 안, 시작·끝 고도 차 ≤ 0.1 m(승강장은 수평), 최소 곡선반경 미만 불가,
  총 굽힘각 ≤ `역길이 / 역 최소반경`(라디안→도). 역이 휘어 있으면 승강장이 안 된다는 뜻.
- **경사**: `|고도차| / 길이 × 100`이 그 열차 종류의 `maxSlopePercentage`를 넘으면 불가.
- **선로끼리 교차/겹침**(`validateTrackOverlap`): 겹치는 두 선로의 교차점 고도 차가 **0.02 m 미만(같은 높이 = 접속)** 이거나
  **`STATION_HEIGHT`(4 m) 이상(입체교차)** 이어야 한다. 그 사이 고도 차이는 오류. 역과는 반드시 4 m 이상 분리. 경사 있는 분기는 미지원 안내.
  선로 두께는 폭의 절반 × 0.5 버퍼로 판정. 다른 열차 종류의 선로는 서로 접속 불가.
- **건물과 충돌**: 오류가 아니라 **철거 대상**(철거 비용 별도 표시, "터널로 지나가면 싸다"는 경고). 고가가 지붕 위 통과 조건을 만족하면 "오버패스"로 분류.
- **수심 충돌**: 선로가 해저 지형보다 위에 있으면 오류 — 해저보다 깊게 가거나, 지면 위 5 m 이상 고가여야 한다.
- 도로 교차: 지표 선로가 도로를 건너면 건널목(열차 종류가 허용할 때만) 비용이 붙음.

### 건설비 산식 (`computeGroupCost`, `getStationAndTrackCostsByType`, index 138344~138460행)
- **선로 묶음 비용** = `길이 × 열차 종류 기본선로단가 × 차선 배수(1차선 0.75, 4차선 이상 1.5, 2차선 1.0; 차량기지 ×0.5)`
  `× [ 고도 배수(평균 고도) × (100−수면비율)/100 + 수면 배수(평균 고도) × 수면비율/100 ]`.
  평균 고도 = 묶음의 첫 트랙 시작·끝 고도의 평균. 수면비율 = 선로가 물 위를 지나는 비율(%).
- **역 비용** = `열차 종류 기본역단가 × 차선 배수(단선 0.75, 4선 1.5) × 승강장 배치 배수 × 길이 계수` 에 위와 같은 육지/수면 분할.
  길이 계수 = `0.75 + 0.25 × min(승강장이 수용하는 최대 칸수 / 열차 최대 칸수, 1)`(승강장이 짧을수록 싸짐).
- 별도 항목: 건물 철거, 건물 오버패스, 건널목, 스위치(scissors) 크로스오버, 터널 포털(트렌치↔개착 전환), 고가 램프(램프↔고가 전환),
  대심도 TBM 동원비(구간마다), 노면주행.
- 건설은 **블루프린트**(계획선)로 그린 뒤 "Build"를 눌러 확정. 견적은 그리는 동안 항목별로 표시(육지/수면, 공법별 분리).

### 곡선·경사 속도 (`getMaxSpeedForRadiusAndSlope`, index 139490~139525행) — 함수명은 추정 복원
`곡선 속도 = sqrt(최대횡가속 × max(반경, 최소반경))` (역 구간은 ×0.5) `× max(0.5, 1 − (평균 편성 길이)/200)`,
평균 편성 길이 = 열차 종류의 (최소칸수+최대칸수)/2 × 칸 길이. 경사가 최대 경사의 95% 이상이면 최고속도×0.6, 80% 이상 ×0.75,
60% 이상 ×0.9로 추가 제한. 결과는 정수 m/s로 반올림. (`CANT_MECHANICS` 플래그가 켜지면 §0 앞쪽의 캔트 모델로 대체.)
반경은 세 점의 현 길이와 꺾임각으로 계산(`calculateTurnRadius`, 꺾임각 1° 미만이면 직선 취급).

### 신호(폐색) (simEngine 30838~30945행)
- 열차마다 세 개의 **창(window)** 을 계산: 열차 본체(꼬리~머리), 앞쪽 **경고 창 2 m**, 그 앞 **추가 경고 창 100 m**.
  각 창이 지나는 선로 조각과 겹치는 **신호 구역**(`areaCovered`가 트랙 전체이거나 시작~끝 진행률 구간이 겹침)의 신호를 "발동"시킨다.
- 신호 상태는 색 설정 이름으로 보아 세 가지: **Free / Occupied / Reserved**. 열차 투입 검사에서도 `occupations`(점유)와 `reservedBy`(예약)를 본다.
- 합류(V자) 신호 창 200 m, 다이아몬드(교차) 창 10 m, 건널목 신호 반경 200 m는 §1의 규칙값. 단선 상호 반대 방향 열차는 크로스오버가 있어야 회차 가능
  ("Trains need crossovers" 안내문).

### 승객 이동·승하차·수익 (simEngine 32504~32900, 33165~33360행 / index 200613~200680, 210300~210390행)
읽은 방법은 위와 같음(문맥으로 복원). 문자열 배열 인덱스는 실행 시 회전하므로 필드명은 문맥·문자열 목록으로 추정한 부분이 있다.
- **단위는 "pop"(승객 집단)** — 개인이 아니다. pop은 `size`와 미리 계산된 여정 `transitPaths[0].segments[]`(걷기/운전/열차 구간: `routeId`,
  `fromStopId`, `toStopId`, `departureTime`, `arrivalTime`)와 `modeChoice.transit`(=열차를 타는 인원)을 가진다. 열차 탑승 인원은 `modeChoice.transit ?? size`.
- **pop 하나에 movement 하나**: `{updateTrigger, lastUpdated, journeyIndex}`. 트리거는 세 종류.
  - `time`: `seconds < 현재`가 되면 다음 구간으로. 걷기/운전 구간은 이 트리거(첫 구간은 절대 `arrivalTime`, 하차 직후 걷기는 `now + (arrival−departure)`).
  - `train-embark`: (노선 `routeId`, 현재 역) 대기. 그 노선의 **정차 중인 열차**만 후보.
  - `train-disembark`: (`trainId`, 목적 역) 승차 중. 그 열차가 정차 중이고 그 역에 서 있을 때 하차.
- **탑승 조건** (`findTrainPopCanBoard`): 열차가 (a) 이 역에 정차 중, (b) 목적 역이 열차의 "앞으로 방문할 역" 중 **첫 구간**(같은 역이 다시 나오기 전까지)에 있음 — 왕복 노선에서 반대 방향으로 가는 열차에 잘못 타지 않게 하는 장치, (c) 용량: `현재 승차 − 이 역에서 내릴 인원 + 이번 틱에 이미 예약된 승차 + 이 pop 크기 ≤ maxCapacity`. **집단 전체가 타거나 아예 못 탄다(분할 없음).** 첫 조건을 만족하는 열차가 여러 대면 목록 순서대로 첫 열차.
- **하차**: 열차 정차 확인 → 용량 변경 −size → 다음 구간이 걷기/운전이면 time 트리거, 열차면 embark(환승), 없으면 여정 완료.
- **잔여 용량 경고**: 승차 후 `maxCapacity − 승차인원 ≤ getCapacityWarningThreshold()`이면 "trains-at-capacity" 경고(10초 버킷으로 중복 제거).
- **역 대기 경고** (`getStuckPassengerWarnings`): 역별 대기 인원이 100/200/500/1,000/2,000/10,000/100,000 이상이면 경고(30초 버킷). 문구는 200 이상 "노선 열차 추가 검토", 500 이상·1,000 이상은 더 강한 권고.
- **포기(이탈)는 없다**: 우리 엔진은 25분 대기 후 포기(`ABANDON_AFTER_MINUTES`)하지만 게임은 대기 시간 제한이 없다. 대신 **1시간마다** `lastUpdated`가 12시간(`MAX_JOURNEY_DURATION_SECONDS`) 넘은 movement를 삭제(정지 pop 청소).
- **열차가 삭제되면** 그 열차에 탄 pop의 movement는 즉시 삭제(승객 소멸, 수익 없음). 노선이 바뀌어도 여정 재계산은 하지 않는다 — 경로는 출발 시점에 고정.
- **출발 시각**: 15분마다(`elapsedSeconds % 900 == 0`, `AUTO_SIM_COMMUTES`일 때) 이동 중이 아닌 모든 pop에 대해 (집 출발 시각 − 현재 하루 시각)이 0~900초 안이면 "집→직장", 직장 출발 시각이 그 안이면 "직장→집"으로 `popsToStartJourney`에 넣어 popCommute 워커(경로탐색)로 보낸다. 즉 **pop마다 하루 두 번의 고정 출발 시각**이 있다.
- **갱신 주기**: movement 처리는 `updateInterval` 틱마다·15분 경계·배치 마지막 틱에 돈다(매 틱 아님). 지도용 pop GeoJSON은 66 ms 이상 간격으로만 만든다(표시용).
- **수익은 여정 완료 시점에 정산**(`updateStats`): `Σ (modeChoice.transit × fareCost) × FARE_MULTIPLIER`. `fareCost`는 여정에 붙은 값(`transitPaths[0].fareCost`)이 있으면 그것, 없으면 기본 운임(`transitCost`). 노선별 수익은 `computeJourneyFareBreakdown`으로 구간 안분(안 되면 이용 노선 균등 분배). 승객 통계에는 pop 크기·출발/도착 시각·`origin`(home/work, 출발 시각이 집·직장 출발 시각 중 어디에 더 가까운지로 판정)을 기록. **탑승이 아니라 도착해야 돈이 들어온다.**
- **열차 운영비**: 열차당 `(고정비 + 량수 × 량당비) × TIME_FARE_MULTIPLIER`를 시간당으로, 15분마다 경과 시간만큼 청구. 차고에 주차된 열차는 청구하지 않는다. 노선별 비용도 따로 집계.
- **유지비**: 5분마다 `트랙·역·건널목 유지비 × (1/86400) × 계수`를 경과 시간분만큼 청구(일 단위 요율을 시간 비례로 환산).
- **미인증 시 수익 절반**: `updateStats`는 브라우저 저장소의 특정 항목(`L_CHECK`)이 없거나 5자 미만이면 수익을 ×0.5 한다. 데모/미인증 페널티로 보이며 우리 엔진에는 해당 없음(재현하지 않는다).
- **우리 엔진과의 차이 (passengers.mjs)**: ① 개인 vs 집단(pop, 분할 불가 승차) ② 25분 포기 vs 무제한 대기(경고만) ③ 승차 순서 배열 순서 vs 열차 목록 순서, 용량 예약 없음 vs "내릴 인원 차감+예약" ④ 방향 판정 `alightIndex` 비교 vs "앞으로 방문할 첫 구간" 집합 ⑤ 매 스폰 시점 경로탐색 vs 하루 2회 고정 출발 시각·15분 배치 ⑥ 재경로(`retryPendingRoutes`)는 게임에 없음 ⑦ 수익 정산(도착 시 운임) 자체가 없음.

  `BASE_CTILES_API_URL = https://ctiles.subwaybuilder.com`, 일부 `tiles/prism.subwaybuilder.com`)라서 설치본에는 내려받은 TOK/OSA/NAG만 있고 런던은 없다.
  기본 미션 정의도 서버 쪽으로 보이며(설치 폴더·번들에서 히드로/LHR 문자열 0건), 모드가 등록하는 미션의 **형식**은 코드에 있음(아래).

### 모딩 API·커리어 미션 형식 (index 186578~186643, 191687~ 행) — 우리 미션/시나리오 데이터의 참고 형식
- `window.SubwayBuilderAPI`: `registerCity`(도시 코드·이름·난이도·건물 줌 오프셋 검증), `modifyConstants`(RULES에 deepMerge, `STARTING_MONEY` 등 즉시 반영),
  `modifyColors`, `modifyPathfindingRules`, `registerNewspaperTemplates`, `map.registerLayer/Source/Style`, career·demand·build-automation 하위 API, `reloadMods`.
- **미션 = `{id, cityCode, name, stars[≤3]}`**, 별 하나 = `{id, label, shortLabel, icon, metric, operator, target}`. 별이 3개 초과이면 등록 거부.
  - 지표(`METRICS`): `stations_count`, `trains_count`, `routes_count`, `tracks_count`, `total_passengers`, `ridership_percentage`, `daily_profit`,
    `total_revenue`, `total_debt`, `money`, `play_time_minutes`, `elapsed_days`.
  - 연산자: `>=`(기본) `>` `<=` `<` `==` `!=`.
  - 내부 표현은 `{seed, cityCode, cityName, stars:[{id,label,shortLabel,icon,condition:{type:"metric",metric,operator,value}}]}`.
  → 우리 엔진에서 "히드로 연결" 같은 시나리오 목표는 **지표 임계값 3개(별 3개)** 로 표현하면 게임과 호환된다.
- `FARE_MULTIPLIER`(365)의 정체: 코드상 `FARE_MULTIPLIER = GOVT_FARE_MULTIPLIER(1) × TIME_FARE_MULTIPLIER(365)`이고 열차 운영비(`getTrainCost`)에도 같은 `TIME_FARE_MULTIPLIER`가 곱해진다.
  즉 **수익과 운영비를 같은 365배로 키우는 경제 스케일**(정확한 의도는 코드 주석이 없어 미확인). 영상 화면의 운영비 `$273,750/hr`(5칸)도 365의 배수(=750×365).
  v1.7.1 코드값으로 계산하면 (250 + 5×25) × 365 = 136,875로 영상 값의 절반이라 **영상도 옛 빌드**로 보인다(기본 상수가 빌드마다 다름 → 영상 수치를 그대로 정답지로 쓰지 말 것).

### 튜토리얼 클립 4개 (`tutorial-hints/*.mp4`, 7~10초, ffmpeg로 로컬에서 1fps 프레임 추출해 확인)
- **역 배치** (`sb-tut-001`, `002-station2`): 마우스 위치에 역 미리보기와 라벨 `47 km/h / 10 cars / $50.42M`. 승강장 길이를 15칸으로 늘리면 `$55.00M`.
  → **역 비용 산식의 구조가 수치로 검증됨**: Heavy Metro는 최대 15칸이라 `55.00 × (0.75 + 0.25 × 10/15) = 50.42`(비율 0.9167 정확히 일치).
  단, 설치본(v1.7.1) 코드의 Heavy Metro 기본 역단가는 **$60M**이고 클립은 $55.00M이므로 **클립은 옛 빌드**로 보인다(절대값은 빌드마다 다름, 산식 구조는 동일).
  `47 km/h` = Heavy Metro의 **정거장 구간 속도 한도 13 m/s(46.8 km/h)** — 확인됨(`maxSpeedLocalStation`). 건설 패널: Build Stations(단축키 2)/Build Tracks(1), Undo/Redo(Ctrl+Z), Cost 탭.
- **선로** (`002-track`): 그리는 동안 라벨 `89 km/h $20.15M`(직선) → 굽으면 `61 km/h $31.56M`. 89 = 최고속도 24.72 m/s, 61 = **정수 m/s로 반올림한 17 m/s(61.2 km/h)** — 곡선 속도가 정수 반올림이라는 해독과 일치. 라벨은 **구간 최고속도와 견적**이며,
  곡선이 늘면 속도↓·비용↑. 선로가 지나는 **건물은 주황/빨강으로 강조**(철거 대상), 가능 여부에 따라 라벨 색이 바뀜(붉은 라벨 = 설치 불가/경고 상태로 추정).
  선을 끝까지 그리면 역 이름(예: `42 St`)이 선 위에 표시됨.
- **노선 만들기** (`002-makeroute`): 하단 탭 6개 = Construction / Routes / Demand Stats / Route Intensity / Station Ridership / Journey Planner.
  Route Form: 이름(선택), **20색 팔레트 + 커스텀 색**, 글자색(흰/검), **모양(원·마름모·사각·삼각 등)**, 열차 종류. Route Details: Stations / Trains 탭, Edit route.
- 클립 배경은 뉴욕(Midtown/Murray Hill 등)이라 게임 내 튜토리얼 도시는 설치본과 별개. 우리 쪽에 필요한 것은 "UI 순서"뿐이라 도쿄 적용에는 영향 없음.
- **실제로 막힌 것은 둘뿐**: 메인 프로세스 `main.jsc`(V8 바이트코드)와 번들 코드 실행(자동 분류기가 거부).

## 3. 우리 엔진과의 차이 (`transitline/engine`)

| 영역 | 게임 | 우리 (현재) | 격차 |
|---|---|---|---|
| 역/선로 배치 | 자유 배치, 지형·건물·물 위 검증 | 팩의 demand point에만 연결 | **가장 큼** |
| 건설비 | 고도 7단계 × 수심 배수 × 열차 종류 | 없음(management/는 별개 JPY 입찰 게임) | 큼 |
| 열차 물리 | 가감속, 저크, 곡선 속도, 신호 | 등속, 신호 없음 | 큼 |
| 수요 | 200명 pop, 15분 릴리스, 5단계 시간대 | 중력/OD, 캘린더 계수, 규모는 가시성용 축소 | 중간 (데이터는 이미 있음) |
| 경로 | rRAPTOR 시간표 | Dijkstra + 환승 페널티 | 중간 |
| 수단 선택 | 소득 기반 체감시간 | 잡음 섞은 최소시간 | 중간 |

| 지도 | 실제 도로/건물/해안/수심 | 초기 팩은 추상 좌표, 도쿄 팩은 있음 | 도쿄 팩에서는 데이터가 준비됨 |

## 6. 도쿄(일본 지하철) 방식에 맞추기 (우선 적용 방향)

원칙: 게임의 **함수 구조**(수단 선택 산식, 요금 그룹, 시간대 틀, 열차 물리)는 골격으로 삼고, **파라미터와 규칙은 도쿄 실데이터**로 교체한다
(실데이터 우선 방침). 아래 수치가 없는 칸은 일부러 비워 뒀다 — 출처를 확인한 뒤에만 채운다.

**이 저장소에서 확인한 사실**
- `packs/tokyo/existing-network.json`: 노선 195개, 사업자 문자열이 다양하고 `東急電鉄;東京地下鉄;東武鉄道`처럼 **여러 사업자가 한 노선에 묶인 경우**(직통운전)가 있다.
  단, `stationIds`가 `ward-koto`, `kanto-13229` 같은 **수요 지점(구/시정촌 단위)** 이라 실제 역이 아니다.
- `engine/src/management/country-profiles.mjs`: JP 프로필(통화 JPY, 환승 정산 `transferSettlement: true`, 대심도 이용 가능)이 이미 있다.
- `engine/src/management/construction.mjs`: JPY 공법별 km당 단가표와 1435 mm/20 m 차량 프로파일이 있다(단가표의 출처는 미확인 → 근거 확인 필요).

**우선순위(도쿄 기준)**
1. 실제 역 단위 기존망(사업자·직통 포함) 구축 — 이게 없으면 요금·환승·급행 모두 모델링이 무의미.
2. 요금 그룹 + 거리 구간표 + 환승 공제.
3. 직통운전(요금 그룹의 구간 단위 부여).
4. 차량 프로파일 + 혼잡률로 정원 보정.
5. 수단 선택 파라미터 재보정 후 PT조사 수단분담률과 대조.
6. 급행/완행: 정차역 목록이 다른 노선을 같은 선로에 겹치는 방식으로 설계(게임에서 예시 확인 후).
