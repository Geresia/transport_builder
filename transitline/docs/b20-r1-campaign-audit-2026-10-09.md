# B20-R1 30년 캠페인 저장·복원·성능·결정성 감사

기준은 master `cc32ecb`(B20 M1·E1·E2·E3·M2·M3 포함). 30년 = 360개월 = 10,800일 = 15,552,000분, 분기마다 마일스톤 하나(120개)인 프로그램 하나를 실제 `ScenarioRuntime`에서 끝까지 돌렸다(`engine/test/b20-campaign-audit.test.mjs`, 9개). 감사에서 **결함 3개를 찾아 고쳤고**, 고치지 않고 기록만 한 것이 있다.

## 결론: 시민 시뮬레이션도 하루 단위 반복도 필요 없다

- 30년은 경영 시계를 **360번**(월 단위) 앞으로 보내고 분기마다 마일스톤 명령 120번을 내는 것이 전부다. 운영 시계(`simMinutes`)·열차·승객·난수·원장은 한 번도 움직이지 않으며, 운영 상태는 30년 뒤에도 시작과 **바이트 단위로 같다**(테스트가 검사).
- 캠페인 모듈(`campaign-*`, `management/campaign-*`, `map/regional-development-program*`)에는 일 단위 루프, 시뮬레이션 호출, 시민·agent 이름, 난수·벽시계가 없다(소스 검사 테스트).
- 시간 축은 기존 경영 시계의 월(30일) 위의 라벨이다. 360개월의 모든 경계(월 시작 분, 그 직전 분)에서 월·연·분기 번호가 정확하고, `targetMonth` `0`(명시된 0)과 `null`(미상)이 구분된다.

## 측정 (같은 기계, 합성 프로그램 1개 + B19 사슬 1개)

| | 수정 전 | 수정 후 |
|---|---|---|
| 30년 저장 크기 | **5,082,040 B** | **106,635 B** |
| 30년 실행 시간 (360개월 + 마일스톤 120) | 3,978 ms | 284 ms |
| 마일스톤 명령 1건 (처음 10건 평균 → 마지막 10건 평균) | 4.9 ms → **74.0 ms** | 2.6 ms → 3.2 ms |
| 저장 / 불러오기 | 95 ms / 30 ms | 3 ms / 4 ms |
| `report()` / `campaignFactReport` | 10 ms / 1 ms | 12 ms / 2 ms |

수정 전에는 프로그램 하나만으로 5 MB가 되었고, 프로그램이 여러 개면 곱으로 커진다.

## 발견 사항

### F-5 (고침) 캠페인 명령의 이벤트 로그가 기록 전체를 담아 저장이 제곱으로 커졌다 — 높음

`ManagementGame.transact`는 명령의 반환값 전체를 이벤트 로그에 넣는다. 마일스톤 명령의 반환값은 **프로그램 기록 전체**(마일스톤 120개 + 이력)라서, 로그는 명령마다 커지는 기록의 사본을 쌓았다(120번 × 수십 KB). 이벤트 로그는 모든 스냅샷에 들어가고 모든 `transact`가 스냅샷을 찍으므로, 저장 크기와 **이후 모든 명령의 비용**이 함께 커졌다(마지막 명령이 첫 명령의 15배).
수정: `transact(type, action, summarize = null)`에 선택 인자를 더하고, 캠페인 명령 10곳이 "누가·어느 상태·방금 한 전이 하나"만 남긴다(`campaignProgramEvent`, `campaignActivationEvent`). 인자를 안 주면 동작은 그대로이고, 캠페인 이벤트 데이터를 읽는 코드는 없다. B19의 이벤트도 기록 전체를 담지만 개발·분담금·승인 기록은 작고 전이 수가 한정되어 이번에는 그대로 두었다(아래 "남은 위험").

### F-1 (고침) 저장 바이트의 키 순서가 상태의 이력에 따라 달랐다 — 중간 (B19-R1에서 발견)

로드 뒤에 처음 생기는 운영 상태 키(B15·B19 적용 기록 등)가 로드하지 않은 실행과 다른 자리에 놓여, 같은 내용이 다른 바이트가 될 수 있었다. 수정: `snapshotOperationalState`가 일반 키를 **정렬해서** 내보낸다(`stations`·`demandNodes`·`rngState`는 늘 맨 뒤). 키 순서만 바뀌고 내용·복원 동작은 같다. 이제 로드 → 저장은 고정점이고, 30년 캠페인을 10년·20년에 끊어 저장·로드하며 이어 간 결과는 끊지 않은 실행과 **바이트까지 같다**. 테스트는 로드 뒤에 B19 수요 원천을 처음 적용하는 경우를 직접 만들어 수정 없이는 실패함을 확인했다.

### F-4 (고침) 실제 런타임에서는 캠페인 활성화를 기록할 수 없었다 — 높음

`ScenarioRuntime.recordCampaignActivation`·`assessCampaignActivation`·`campaignActivationReport`·`campaignFactReport`가 하나의 `geometry`를 **프로그램 지도 검사**(`transitline.regional-development-program/1`)와 **B19 승인 검사**(신도시 개발 지도) 양쪽에 넘겼다. 한 값이 두 문서일 수 없으므로 프로그램 지도를 주면 B19 쪽이 `geometry-schema-invalid`로 `unverified`가 되고, 신도시 지도를 주면 프로그램 쪽이 `program-geometry-invalid`가 되어 **활성화가 절대 기록되지 않았다**(기존 테스트는 가짜 intake로 게임 층만 검사해 놓쳤다).
수정: 네 메서드가 선택 필드 `developmentGeometry`(B19 개발 지도)를 받는다. `geometry`는 그대로 프로그램 지도이고, `developmentGeometry`를 안 주면 예전처럼 `geometry`를 쓴다(그 경우 B19 쪽은 정직하게 `unverified`). **호스트(Codex)는 활성화·보고서 호출에 `{ geometry: 프로그램 지도, developmentGeometry: 신도시 지도 }`를 함께 넘겨야 한다.**

### 고치지 않은 것

- **F-3 시나리오 팩 검사는 B19-E5에만 있다** (B19-R1 문서 참고). 다른 팩에서 그린 개발이 E3 release까지 갈 수 있다. 캠페인은 프로그램 지도의 팩을 `geometry-source-pack-changed`로 검사하므로 B20 쪽은 막혀 있다. 소유자 판단 대기(todo 테스트 남아 있음).
- **단독 `ManagementGame.save()`는 `savedAt`(벽시계 시각)을 넣는다** (`management/core.mjs`). 게임이 쓰는 통합 저장(`ScenarioRuntime.save` → `saveIntegratedGame`)에는 없고, 위 바이트 결정성 테스트가 이 경로를 검사한다. 단독 경로를 파일 비교에 쓰는 곳이 생기면 그때 제거한다.
- **`load` 뒤 첫 저장에 `operationalTimetableWarnings: []`가 붙는다** (기존 동작). 한 번 로드한 뒤에는 고정점이므로 테스트는 "끊지 않은 실행도 한 번 로드·저장해서" 비교한다.

## 남은 위험 (측정 기준)

- `transact`는 매번 **전체 스냅샷을 복제**한다(비용 ∝ 상태 크기). 지금 30년 캠페인 상태는 107 KB라 3 ms 수준이지만, 원장·이벤트가 큰 실제 운영 30년(D0 §4.2의 0.5초/건)에서는 별도 측정이 필요하다. 이 감사는 캠페인과 B19 사슬만 쟀다.
- B19 이벤트(개발·분담금·승인)도 기록 전체를 로그에 담는다. 개발 기록이 수십 KB로 자라는 일은 없지만, 개발이 수백 개가 되면 같은 방식의 요약이 필요해질 수 있다.
- 프로그램 수나 마일스톤 수를 더 늘린 규모(수십 프로그램 × 120)는 재지 않았다. 저장 크기는 명령 수에 선형이라는 것만 검사했다(전반 15년 대비 후반 15년이 160% 미만).

## 검증

`engine/test/b20-campaign-audit.test.mjs` 9개: 시간 축, 30년 실행(운영 상태 불변·난수/돈 불변·이벤트 요약·크기·비용), 끊어서 이어 가기 바이트 일치, 로드 뒤 처음 생긴 키, 중간에 프로그램 지도가 바뀐 경우(전진 불가·되돌림 없음·지연/취소 가능), 실제 런타임의 활성화(두 지도), 캠페인 이전 저장본, 팩트 보고서·참조 목록의 입력 순서 독립, 일 단위·시민 단위 작업이 없음. 수정 없이는 F-5, F-1 두 테스트가 실패함을 확인했다.
