### 후속 설계 반영 사항

사용자와의 후속 논의에서 도시·자동차 도로는 유지하고 버스·철도망만 설계 대상으로 확정했다. 설계 자유를 중심에 두며 기존망 유지/초기화, 자금 제한, 자유 플레이/시나리오는 별도 설정이다. 시설 건설과 차량 제작은 게임 내 시간이 걸리는 프로젝트로 다루고, 차량기지·제작사·시공사와 개통 준비를 연결한다. 여섯 설계 시스템의 통합 기준은 [종합 설계보고서](railway-construction-master-report-kr-jp-2026.md), 상세 분류는 [철도 기본요소 명세](railway-system-foundations.md)를 따른다. 아래 단계표는 초기 제안으로, 첫 지원 범위를 정한 후 단계별 완료 기준을 갱신해야 한다.

## 1. 목표와 범위

도쿄권 철도망을 직접 설계하고 운영하면서, 접근성·수송량·건설비·운영비 사이의 선택을 하는 게임을 만든다.

첫 번째 완성 목표는 다음 사이클을 저장·불러오기까지 포함해 반복할 수 있는 시스템이다. 완성 여부는 지도 화면이 아니라 상태·이벤트·계산 결과로 판정한다.

**수요 확인 → 역·선로 계획 → 비용 확인·착공 → 개통 → 차량 배치·운행 → 수입·혼잡·운영비 확인 → 개선·재투자**

기존 자체 `engine/`를 발전시키는 계획이며, 외부 게임 모드 개발로 전환하는 계획은 아니다. 현재 Vanilla JS ES modules 구조를 유지하고, 프레임워크 교체는 이 로드맵에 포함하지 않는다.

지도 렌더링, 지도 위 역 배치 도구, 선로 드로잉, 카메라, 타일, 지리 데이터 가공은 이 로드맵의 구현 대상이 아니다. 지도 쪽에서 전달한 건설 계획과 구간 특성을 받아 규칙을 적용하고 결과를 반환한다. 핵심 계산은 DOM·Canvas·MapLibre에 의존하지 않는다. 외부 입력의 형식·단위·유효성은 시스템 경계에서 검사한다.

예: 지도 쪽이 길이 1,200m, 공법 지하, 제약 정보가 포함된 건설 계획을 전달하면, 우리 시스템이 건설 가능 여부·비용·공기를 반환한다. 착공 명령을 받으면 자금과 프로젝트 상태를 변경한다. 경로를 지도에 그리거나 원본 지형에서 길이·충돌 정보를 추출하는 작업은 맡지 않는다.

## 2. 단계 요약

| 단계 | 목적 | 플레이어가 확인할 결과 | 통과 기준 |
|---|---|---|---|
| M0 | 범위·단위·데이터 계약 확정 | 무엇을 짓고 어떤 비용을 지불하는지 명확함 | 엔티티·단위·기본 규칙·협업 경계 문서화 |
| M1 | 기존 엔진 안정화 | 배속이나 날짜 경과 때문에 운행 결과가 틀어지지 않음 | E-01~E-07 대응 및 회귀 테스트 |
| M2 | 건설·운영·회계의 공통 기반 | 수요 지점과 역이 분리되고 게임 상태를 저장 가능 | 상태·명령·원장·난수·저장 복원 검증 |
| M3 | 건설 처리 시스템 | 입력된 계획을 검증하고 돈을 들여 개통 가능 | 명령으로 견적부터 개통·취소까지 한 사이클 |
| M4 | 차량·운영 경제 구현 | 차량 구매, 배차, 수송, 수입·지출, 재투자가 연결됨 | 소규모 시나리오에서 전체 경영 사이클 완성 |
| M5 | 건설 공학·서비스 깊이 확장 | 지상·고가·지하 및 환승·혼잡의 선택에 의미가 생김 | 공법·제약·운행 결과가 일관되게 연결됨 |
| M6 | 시스템 통합·부하·장기 검증 | 대규모 운행과 경영 계산이 안정적으로 지속됨 | 지도 없는 재현 가능한 성능·장기 실행·저장 검증 |

M4를 첫 경영 사이클이 완성되는 시스템 버전의 완료선으로 삼는다. M5~M6은 규칙의 깊이와 처리 규모를 확장하는 단계다. 지도 연결 일정과 독립적으로 합성 시나리오에서 개발한다. 기간은 추정치를 확정하지 않고, 단계별 완료 기준으로 진행을 판단한다.

## 3. M0 — 범위와 계약

### 작업

- 외부에서 제공하는 구간 길이·높이는 미터 단위로 통일한다. 좌표 변환과 지형 추출은 지도·데이터 쪽 책임이다. 시간은 시뮬레이션 초, 날짜는 24시간과 영업일 규칙을 구분한다.
- 통화와 가격표를 설정으로 분리하고 금액은 최소 화폐 단위의 정수로 관리한다. 초기 비용 수치는 게임 조정용 값이며 실제 공사비라고 표시하지 않는다.
- 화면의 승객 표시 수와 시뮬레이션 수송 인원을 분리한다. 집단 승객을 사용할 경우 인원 가중치가 차량 정원·통계·운임에 일관되게 반영되도록 규칙을 정한다.
- 수요 지점, 역, 선로 구간, 운행 노선, 차량, 건설 프로젝트, 거래 원장을 구분한다.
- 기존 철도망을 플레이어 자산으로 시작할지, 외부 교통망으로 취급할지 결정한다. 당장 검증할 기본 시나리오는 빈 지도에서 시작하는 방식으로 제안한다.

### Claude와 확인할 최소 계약

| 엔진이 필요한 정보 | 엔진 쪽 책임 | 자료가 없을 때의 원칙 |
|---|---|---|
| 수요·OD·특수 수요와 접근 가능한 역 후보 | 수요 생성, 후보 중 이용 역 선택, 시간대 적용 | 합성 테스트 자료로 개발하고 품질 상태 반환 |
| 구간 길이·고도·수역 등 정규화된 구간 특성 | 공법별 허용 조건·비용·공기 계산 | 0이나 육지로 묵인하지 않고 미확인 상태 반환 |
| 지도 쪽이 추출한 장애물·간격·충돌 후보 정보 | 건설·철거 정책 적용 | 필수 제약 정보가 없으면 확정 건설 제한 |
| 보행 가능 연결과 소요시간 | 접근·환승을 포함한 교통 경로 선택 | 미확인 연결을 임의로 통행 가능 처리하지 않음 |
| 기존 철도망 | 초기 운행망 또는 배경망으로 변환 | 소유권·자산 가치·비용 부과 정책을 분리 |
| 팩 ID·버전·출처 | 저장 호환성 확인 및 조회 API로 메타데이터 전달 | 팩 불일치를 조용히 무시하지 않음 |

정확한 필드와 함수 이름은 현재 팩 형식 확인 후 정한다. 엔진 개발을 위해 데이터 생성 스크립트를 런타임에 편입하지 않는다. 기존 저장소의 데이터·엔진 분리 원칙을 유지한다.

### 완료 기준

- 위 단위와 기본 정책이 문서화되어 있고, 엔진 테스트에 사용할 소형 합성 자료가 정의되어 있다.
- 실제 자료가 필요한 기능과 자료 없이 구현할 수 있는 기능이 구분되어 있다.

## 4. M1 — 엔진 안정화

### 작업 순서

1. 검토 당시 재현 사례를 영구 회귀 테스트로 옮기고 통합 테스트 실행 명령을 추가한다. 재현을 위해 난수 발생기를 주입하고 고정 시드를 지원한다.
2. 고정 간격 시뮬레이션과 렌더링을 분리한다. 큰 시간 간격에서도 이동·정차·배차 이벤트를 누락하지 않는다. 백그라운드 탭의 시간 진행 정책도 명시한다.
3. 24시간 달력과 심야 영업일 처리를 수정한다.
4. 운행 중단 노선, 첫 탑승·환승 대기, 양방향 탑승 가능 여부를 경로 선택과 맞춘다.
5. 대기 시작 시각, 승객 위치, 노선 삭제·변경, 동일 지점 이동을 수정한다.
6. 경로 캐시와 네트워크 버전 관리를 추가한다. 시간대·배차·노선 변경 시 필요한 캐시가 무효화되는지 검사한다.

### 완료 기준

- 동일 난수·명령·시뮬레이션 시간으로 실행하면 1x·2x·4x와 렌더 프레임 변화에도 동일 결과가 나온다.
- 열차가 구간을 건너뛰거나 승객이 삭제된 열차에 남지 않는다.
- 여러 날 실행해도 출근·퇴근 시간대가 이동하지 않는다.
- 기존 테스트와 E-01~E-07 관련 회귀 검증이 통과한다.
- 현재 도쿄 그래프를 고정한 경로 탐색 벤치마크를 남긴다. 성능 목표치는 재현 가능한 기준 장비·입력 확정 후 정한다.

## 5. M2 — 공통 게임 상태·회계·저장 기반

### 작업

- 수요 지점과 실제 건설 역을 분리하고 접근 연결을 별도로 둔다. 기존 팩은 변환 계층을 통해 계속 실행되게 한다.
- 물리적인 선로 구간과 그 위를 운행하는 노선을 분리한다. 선로 길이를 비용·열차 이동·운영비 계산의 공통 기준으로 사용한다.
- UI는 건설·구매·배차 변경 같은 명령을 보내고 엔진이 유효성을 검사한 뒤 상태를 변경하도록 한다.
- 최소 거래 원장을 먼저 만든다. 초기 자금, 건설 지출, 환불을 기록하고 잔액을 원장에서 설명할 수 있게 한다.
- 실행 중 난수 상태, 시각, 진행 중 프로젝트, 차량·승객 상태, 원장을 포함하는 버전 있는 저장 형식을 만든다.
- 건설 명령의 중복 실행과 저장 복원으로 같은 금액이 두 번 청구되지 않게 한다.

### 완료 기준

- 실패한 건설 명령은 돈만 차감하거나 시설만 생성하지 않는다.
- `기초 잔액 + 수입 - 지출 = 현재 잔액`이 항상 성립한다.
- 같은 저장본에서 같은 명령으로 진행하면 동일 결과가 나온다.
- 저장 후 복원한 실행과 중단 없이 이어간 실행의 핵심 상태가 일치한다.

## 6. M3 — 건설 처리 시스템

### 첫 구현 범위

- 역·선로 계획의 생성·수정·삭제 명령 처리. 지도상 배치와 경로 작성 도구는 제외
- 입력된 거리·역 수·공법별 견적과 비용 내역 반환
- 잔액·연결 관계·제공된 제약 정보 검사와 건설 불가 이유 반환
- 계획 → 착공 → 공사 중 → 개통 상태와 예상 완료 시각
- 착공 시 비용 차감, 취소 시 환불 정책, 개통된 시설만 운행 가능
- 역과 선로를 공유하는 노선의 참조 관계 관리. 운영 중 철거는 안전한 중지 절차를 요구
- 외부 UI가 사용할 견적·착공·취소·상태 조회 API. 지도 없는 자동 테스트에서 검증

첫 버전은 기본 지상 공법의 단순 구간으로 제한한다. 수역·건물·급경사 등 지원하지 않는 조건은 막고 이유를 표시한다. 복잡한 공학을 지원하지 않는다고 해서 모든 곳을 건설 가능으로 처리하지 않는다.

### 완료 기준

- 빈 시스템 상태에서 역 3개와 연결 선로의 계획 명령을 입력하고, 견적 확인 → 착공 → 개통할 수 있다.
- 미개통 구간을 열차나 승객 경로가 사용하지 않는다.
- 자금 부족·중복 클릭·취소·저장 복원에서도 자산과 잔액이 어긋나지 않는다.

## 7. M4 — 차량·운영·경제

### 작업

- 차량 구매, 편성 구성, 노선 배치, 필요 편성과 보유 편성의 차이 표시
- 차량을 왕복 후 소멸하는 효과가 아니라 보유 자산으로 관리하고, 운행 종료 후 회수·재배치
- 시간대별 목표 배차와 실제 가능한 배차 구분. 차량이 부족하면 무한 생성하지 않고 공급 부족 표시
- 정원·대기열·만차 미탑승·환승·도착 결과를 집계
- 운임 수입, 차량 운행비, 역·선로 유지비를 원장에 기록
- 현금 잔액, 건설 지출, 영업 수입·지출, 일별 영업손익을 구분해 표시
- 역별 대기 인원, 노선별 이용량·혼잡·운영비, 대중교통 분담률 제공
- 적자·자금 부족 경고. 첫 버전의 파산·운행 중지 규칙은 단순하게 명시하고 채권은 넣지 않음

요금 부과 시점과 환승 정책은 구현 전 확정한다. 기본 제안은 하나의 연속 대중교통 여정에 한 번 청구하는 단순 요금이다. 중도 포기·환불·노선별 수입 배분도 별도 규칙으로 정해 중복 수입을 막는다.

### 완료 기준 — 첫 경영 사이클 완성

- 역 3~5개, 노선 1~2개, 환승이 있는 소규모 시나리오에서 건설·개통·운행·수입·재투자가 연결된다.
- 차량을 추가하거나 배차를 바꾸면 공급과 운영비가 함께 변한다.
- 배속이나 저장·불러오기로 수입·비용이 중복 발생하지 않는다.
- 시뮬레이션 7일 실행에서 승객·차량·자금 불변식이 유지된다. 흑자·적자와 무관하게 결과의 원인을 통계·원장·이벤트로 설명할 수 있다.

이 단계의 표시·경고는 우선 조회 결과와 이벤트로 제공한다. 실제 경영 패널의 화면 구성은 별도 UI 작업이며 지도 편집 기능을 포함하지 않는다.

## 8. M5 — 건설 공학과 서비스 깊이

### 확장 후보와 순서

1. 지상·고가·지하 공법별 비용·공기·유지비와 고도 전환
2. 제공된 고도·수심·안전 간격·경사·곡선·접속 정보를 사용하는 허용 규칙
3. 교량·하저 터널의 건설 조건·비용·공기 규칙. 수역 지오메트리 분석은 제외
4. 가감속·역간 거리·곡선·경사에 따른 주행시간
5. 제공된 도보·환승 연결을 이용하는 승객 선택 정교화, 시간대별 혼잡과 서비스 지표
6. 별도 검증 후 선로 공유 용량·최소 열차 간격·분기 충돌 처리

각 기능은 견적·실제 소요시간·원장·운행 결과가 같이 바뀌도록 완성한다. 정밀 폐색·신호, 입체 복합역 등은 자동으로 포함하지 않고 별도 범위로 결정한다.

### 완료 기준

- 같은 연결을 서로 다른 공법으로 계획하면 비용·공기·유지비 차이를 비교할 수 있다.
- 알려진 불가능 조건은 건설 전에 차단되며, 결측 데이터를 안전한 조건으로 오인하지 않는다.
- 입력된 설계 구간 길이가 비용·운행시간·유지비 계산에서 일관되게 사용된다.

## 9. M6 — 시스템 통합·부하·장기 검증

### 작업

- 빈 상태와 초기 자산이 주어진 상태를 각각 검증한다. 외부 기존망을 사용하는 경우 자산 가치가 명시되지 않은 자료로 정밀 건설비를 추정하지 않는다.
- 합성 입력으로 접근 연결·특수 수요·결측값·외부 입력 오류의 처리 계약을 검증한다. 공간 데이터 생성·배분은 여기서 구현하지 않는다.
- 경로 캐시·수요 집계·운행 업데이트를 측정하고 병목을 개선한다. Worker 도입 등은 측정 근거가 있을 때 결정한다.
- 시뮬레이션 틱 처리 시간, 처리량, 경로 탐색 시간, 메모리, 저장 크기·시간을 기록한다.
- 30일 장기 시뮬레이션, 배속, 네트워크 변경, 저장 복원, 팩 버전 불일치, 중복·실패 명령을 지도 없이 검증한다.
- Claude 쪽에서 인터페이스에 맞는 자료를 제공하면 동일 계약 테스트를 적용한다. 지도·서버·뷰어 통합 작업으로 범위를 확대하지 않는다.

### 완료 기준

- 기준 장비와 고정 시나리오에서 합의한 성능 목표를 통과한다.
- 소형·대규모 합성 시나리오의 기능·저장·회계·운행 회귀 테스트가 통과한다. 기존 팩 호환 테스트도 유지한다.
- 알려진 입력 데이터 한계와 미지원 기능이 문서와 API 결과에 드러난다.

## 10. 이번 범위에서 미루는 것

- 채권·금리·세금·보조금·복잡한 기업 회계
- 토지가격 변화·도시 성장·부동산 개발
- 정밀 신호 제어·차량기지 내부 배선·차량 고장 모델
- 캠페인·미션·업적·멀티플레이
- 외부 게임 모드 기능 추가

지도 렌더링·편집·타일·지형 및 공간 데이터 가공은 나중에 우리가 맡을 기능 목록이 아니라 별도 담당 영역이다.

이 기능들은 첫 경영 사이클이 검증된 뒤 별도 로드맵으로 판단한다.

## 11. 첫 작업 묶음

로드맵에 동의한 뒤 가장 먼저 수행할 범위는 M0의 최소 정책 확정과 M1의 시간 처리 안정화다.

- [ ] 기본 시작 모드·시간·인원·금액 단위와 기존망 취급 정책 기록
- [ ] 기존 테스트를 한 명령으로 실행하는 진입점 추가
- [ ] 열차 시간 분할·정차·종점 회차 회귀 테스트 추가
- [ ] 달력 자정·심야·다일 실행 회귀 테스트 추가
- [ ] 고정 간격 업데이트와 열차 잔여시간 처리 수정
- [ ] 24시간 달력·심야 영업일 처리 수정
- [ ] 기존 팩 테스트 재실행 및 결과 기록

여기서는 지도·팩 데이터와 경제 수치를 동시에 바꾸지 않는다. 완료 후 경로·승객 안정화로 이어간다.

## 12. 진행 기록 원칙

- 각 작업은 해당 단계, 수정 파일, 검증 명령, 결과, 남은 한계를 남긴다.
- 문서의 제안과 구현 완료를 구분한다. 테스트 통과 전 완료로 표시하지 않는다.
- 기능을 추가할 때 기존 팩 호환성·저장 복원·회계 불변식을 함께 확인한다.
- 현재 상위 README 일부에는 도쿄 OD가 아직 연결되지 않은 것으로 적혀 있으나, 실제 엔진은 이미 OD와 기존망을 읽는다. 진행 판단은 코드와 테스트를 기준으로 하고, 문서 갱신은 별도 변경으로 관리한다.
