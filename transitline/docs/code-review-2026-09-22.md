# 코드 검토 및 건설·경제 개발 전 보완 목록

- 검토일: 2026-09-22
- 상태: 검토 완료. S-01·S-02·D-01~D-05는 Claude가 수정·검증 완료(커밋 `911394e`, 각 항목 실제 데이터/브라우저로 재현·확인). E-01~E-07(엔진, Codex 담당), D-06·A-01~A-04(버그가 아닌 설계 과제)는 미착수.
- 역할 구분: Claude는 지도·데이터, Codex는 건설·경제·시뮬레이션 담당
- 검토 대상: 자체 엔진, 지도 뷰어, 개발 서버, 팩 생성·검증 코드
- 검토 한계: 모든 소스의 전수 검증이나 브라우저 전체 동작·침투 테스트를 완료한 보안 감사는 아님. 외부 라이브러리 및 생성 데이터 전체에 대한 검증도 아님.
- 코드 위치는 검토 당시 기준이며 이후 수정으로 줄 번호가 달라질 수 있음.

## 결론

건설·경제 시스템을 얹기 전에 시뮬레이션의 시간·경로·승객 처리를 안정화해야 한다. 현재 운행 결과가 프레임 간격이나 달력 처리에 따라 달라질 수 있으므로, 이 상태에서 수익·운영비를 계산하면 경제 모델의 결과도 부정확해질 수 있다.

추천 순서:

1. 엔진 오류 수정
2. 시간·경로·승객 처리 회귀 테스트 확보
3. Claude와 지도·데이터 ↔ 엔진 인터페이스 확정
4. 건설 시스템 구현
5. 경제 시스템 구현 및 균형 조정

## 1. 엔진 문제 — Codex 담당

### E-01. 열차 이동이 프레임 간격에 따라 달라짐

- 우선순위: 높음
- 근거: [trains.mjs](../engine/src/trains.mjs), 47~73행; [loop.mjs](../engine/src/loop.mjs), 17~34행
- 문제: 한 번의 업데이트에서 역 도착을 한 번만 처리한다. 구간 진행률의 초과분을 다음 구간으로 넘기면서 정차시간과 남은 이동시간을 정확히 소비하지 않는다.
- 재현: 같은 65초를 한 번에 처리한 경우와 1초씩 65번 처리한 경우 열차 위치가 달랐다. 한 번에 처리하면 구간 진행률 `t`가 `3.5`까지 올라갔다.
- 영향: 배속·프레임 저하에 따라 이동시간, 수송량, 도착 결과가 달라진다.
- 보완: 고정 시간 간격 시뮬레이션과 남은 이동·정차시간을 소비하는 이벤트 처리를 도입한다. 시간 분할 방식에 따른 결과 일치 테스트를 추가한다.

### E-02. 수요 달력과 게임 시계가 어긋남

- 우선순위: 높음
- 근거: [demand-engine.mjs](../engine/src/demand-engine.mjs), 184~195행; [loop.mjs](../engine/src/loop.mjs), 58~62행
- 문제: 자정 이후까지 이어지는 시간표의 마지막 종료 시각을 하루 길이로 사용한다. 게임 시계는 24시간 기준인데 Corridor 팩의 수요 달력은 25시간 기준이 된다.
- 재현: Corridor 팩에서 1일째 오전 8시는 `am_peak`, 9일째 오전 8시는 `off-hours`, 10일째 오전 8시는 `evening`으로 판정됐다.
- 영향: 출퇴근 수요, 배차 시간대, 향후 일별 결산 기준이 서로 어긋난다.
- 보완: 24시간 날짜와 자정 이후까지 이어지는 영업일을 구분한다.

### E-03. 운행하지 않는 환승 노선도 이용 경로로 선택됨

- 우선순위: 높음
- 근거: [network.mjs](../engine/src/network.mjs), 19~30행; [mode-choice.mjs](../engine/src/mode-choice.mjs), 14~26행
- 문제: 배차가 0인 노선도 경로 그래프에 포함된다. 대기시간은 첫 번째 탑승 노선에 대해서만 계산한다.
- 재현: A→B 노선은 운행 중이고 B→C 노선은 현재 시간대 배차가 0인데도 A→C 이동 수단으로 대중교통을 선택했다.
- 영향: 승객이 오지 않는 환승 열차를 기다리며, 대중교통 이용률과 경로 비용이 왜곡된다.
- 보완: 운행 가능 여부와 환승 대기시간을 경로 비용에 반영한다. 시간대·배차 변경 시 경로 갱신 정책도 정한다.

### E-04. 환승 대기 포기가 실제 대기시간이 아닌 총 여행시간 기준

- 우선순위: 높음
- 근거: [passengers.mjs](../engine/src/passengers.mjs), 50~56행
- 문제: 대기 중 포기 여부를 `현재 시각 - 승객 생성 시각 > 25분`으로 판정한다. 이미 열차 안에서 보낸 시간도 포함된다.
- 재현: 생성 후 30분이 지난 승객을 환승 대기 상태로 두면 즉시 포기 처리됐다.
- 영향: 장거리 이동과 환승의 성공률이 부당하게 낮아진다.
- 보완: 생성 시각, 대기 시작 시각, 누적 대기시간을 구분하고 포기 정책을 명시한다.

### E-05. 노선 삭제 시 승객이 이전 역으로 돌아감

- 우선순위: 높음
- 근거: [state.mjs](../engine/src/state.mjs), 132~155행; [passengers.mjs](../engine/src/passengers.mjs), 62~85행
- 문제: 탑승 중 중간역을 지나도 승객의 `currentStationId`가 갱신되지 않는다. 노선 삭제 시 해당 승객을 그 위치에서 대기 상태로 전환한다.
- 재현: A에서 탑승해 B를 지난 승객이 노선 삭제 후 A에서 대기하는 상태로 돌아갔다.
- 영향: 철거·노선 변경 시 승객 위치와 여행 결과가 잘못 처리된다.
- 보완: 운행 중 위치와 마지막 정차역을 관리한다. 현재 이용 구간과 남은 경로를 기준으로 삭제 영향을 판단하고, 철거 시 승객 처리 정책을 정한다.

### E-06. 출발지와 목적지가 같은 수요에서 예외 발생

- 우선순위: 중간
- 근거: [routing.mjs](../engine/src/routing.mjs), 7행; [mode-choice.mjs](../engine/src/mode-choice.mjs), 26행
- 문제: 동일 지점 경로는 빈 `hops`를 반환하지만 이동 수단 선택에서 첫 번째 노선을 읽는다.
- 재현: 동일 출발·도착 지점으로 호출하면 `Cannot read properties of undefined (reading 'lineId')` 예외가 발생했다.
- 영향: 해당 수요가 들어오면 애니메이션 루프까지 중단될 수 있다.
- 보완: 입력 검증과 동일 지점 이동 처리 규칙을 추가한다.

### E-07. 도쿄 규모에서 경로 탐색 비용이 큼

- 우선순위: 높음
- 근거: [routing.mjs](../engine/src/routing.mjs), 19행부터; [passengers.mjs](../engine/src/passengers.mjs), 17행
- 문제: 승객 발생마다 경로를 다시 탐색하며, 탐색 과정에서 최소 거리 노드를 선형 순회로 고른다.
- 측정: 현재 도쿄 그래프에서 경로 탐색 200회에 약 2.5초가 걸렸다. 이는 검토 환경의 참고 측정값이며 모든 환경의 성능을 보장하는 수치는 아니다.
- 영향: 대규모 수요·배속 운행에서 메인 스레드 병목이 될 수 있다.
- 보완: 네트워크 버전별 경로 캐시, 출발지별 탐색 결과 재사용, 우선순위 큐 기반 탐색을 검토한다. 시뮬레이션과 렌더링 갱신도 분리한다.

## 2. 보안 문제 — 서버·뷰어 담당과 조율

### S-01. 개발 서버의 공개 폴더 밖 경로 접근 제한 누락

- 우선순위: 높음. 단, 현재 서버는 localhost에 바인딩되어 노출 범위가 제한적임.
- 근거: [serve.ps1](serve.ps1), 23~26행
- 문제: URL 경로를 디코딩한 뒤 공개 폴더에 결합하며, 최종 경로가 공개 폴더 내부인지 확인하지 않는다.
- 확인 범위: 인코딩된 상위 경로를 입력했을 때 `transitline/docs` 밖의 프로젝트 루트 `README.md`로 해석되는 것을 확인했다. 실제 HTTP 파일 유출까지 검증한 것은 아니다.
- 영향: 서버 프로세스가 읽을 수 있는 공개 폴더 밖 파일의 노출 가능성이 있다.
- 보완: 최종 절대 경로를 정규화하고 디렉터리 경계를 포함해 공개 루트 내부인지 검사한다. 범위를 벗어난 요청은 거부한다.

### S-02. 외부 데이터 문자열의 HTML 직접 삽입

- 우선순위: 높음. 외부·사용자 제공 팩을 수용하거나 배포하기 전에 조치.
- 근거: [viewer.html](../packs/tokyo/viewer.html), 640~647행, 807~809행, 1016행, 1071~1073행, 1186~1187행
- 문제: 지역명·건물명·종류 등 데이터 문자열을 `innerHTML` 및 팝업 `setHTML`에 직접 삽입한다.
- 영향: 악의적인 문자열이 데이터에 포함되면 DOM XSS로 이어질 수 있는 구조다. 현재 데이터가 악성이라는 의미는 아니다.
- 보완: `textContent` 및 텍스트 노드 기반 DOM 구성을 사용한다. 팝업도 안전하게 구성한 DOM을 전달하는 방식으로 바꾼다.
- 확인 범위: 코드상 삽입 경로를 확인했으며 실제 브라우저 공격 실행은 검증하지 않았다.

## 3. 지도·데이터 문제 — Claude 전달용

### D-01. 여러 외곽 폴리곤을 가진 건물의 면적 계산 오류

- 우선순위: 높음
- 근거: [tokyo-survey-buildings.mjs](../scripts/tokyo-survey-buildings.mjs), 99행
- 문제: 첫 번째 링을 제외한 모든 링의 면적을 구멍으로 간주해 뺀다. 여러 외곽 링이 있는 건물은 추가 외곽 면적도 차감된다.
- 영향: 해당 건물의 면적과 인구·일자리 배분이 왜곡될 수 있다. 현재 데이터에서 영향받는 건물 수와 총량은 별도 집계가 필요하다.
- 보완: 외곽 링과 내부 구멍을 구분해 폴리곤별 면적을 합산한다. 다중 외곽·구멍 포함 사례의 테스트를 추가한다.

### D-02. 일자리 데이터 덮어쓰기 축소 방지 검사 무력화

- 우선순위: 중간
- 근거: [tokyo-demand-jobs.mjs](../scripts/tokyo-demand-jobs.mjs), 35행; [safe-write.mjs](../scripts/safe-write.mjs), 8~18행
- 문제: 개수 계산 콜백이 전달받은 기존·신규 JSON을 사용하지 않고, 바깥의 새 데이터 `text`만 읽는다. 따라서 비교되는 개수가 항상 같아진다.
- 영향: 의도한 데이터 축소 방지 검사가 작동하지 않는다.
- 보완: 콜백 입력으로 개수를 계산한다. 추가로 축소 허용 환경변수는 정확히 `1`일 때만 허용하고, 임시 파일 작성 후 교체하는 저장 방식을 검토한다.

### D-03. 취업자 데이터 불일치를 발견해도 저장 진행

- 우선순위: 중간
- 근거: [tokyo-employed.mjs](../scripts/tokyo-employed.mjs), 61~74행
- 문제: 누락과 지자체 합계 불일치를 계산하지만 저장을 막지 않고 마지막에 로그만 남긴다.
- 영향: 입력 자료에 문제가 생겨도 잘못된 결과가 기존 파일을 대체할 수 있다. 현재 결과 파일에 실제 불일치가 있다는 주장은 아니다.
- 보완: 허용 기준을 넘으면 저장 전에 실패시킨다. 의도된 예외는 명시적으로 기록한다.

### D-04. 검증 캐시의 의존성 누락

- 우선순위: 중간
- 근거: [pack-checks.mjs](../scripts/pack-checks.mjs), 21~32행, 103~111행
- 문제: 일부 검사는 manifest 값에 의존하지만 캐시 입력에는 manifest가 포함되지 않는다. 검사 코드의 버전도 캐시 서명에 반영되지 않는다.
- 영향: 메타데이터나 검사 로직이 바뀌어도 과거 통과 결과가 재사용될 수 있다.
- 보완: 실제 의존 파일과 검사 버전을 캐시 키에 반영한다. 배포 전 검증에서는 캐시를 끄고 실행한다.

### D-05. 건물 표시 토글과 3D 토글의 상태 충돌

- 우선순위: 중간
- 근거: [viewer.html](../packs/tokyo/viewer.html), 1112~1116행, 1201~1208행
- 문제: 건물 숨기기는 3D 레이어를 제어하지 않고, 3D 전환은 건물 숨김 상태를 무시해 레이어를 다시 표시한다.
- 영향: 사용자가 건물을 숨겼는데도 입체 건물이 남거나 전환 후 다시 보일 수 있다.
- 보완: 건물 표시 여부와 3D 여부를 하나의 상태에서 계산해 모든 관련 레이어에 적용한다.

### D-06. 지도 데이터와 엔진 사이의 연결 계약 필요

- 우선순위: 건설 개발 전 확정
- 근거: [pack.mjs](../engine/src/pack.mjs), 25~53행; [state.mjs](../engine/src/state.mjs), 73행
- 현황: 엔진 로더는 수요·OD·기존 노선을 중심으로 읽는다. 지도에 보이는 특수 수요·건물·지형 자료가 곧바로 건설 제약이나 시뮬레이션에 반영되는 구조는 아니다.
- 분류: 확인된 버그라기보다 아직 연결되지 않은 기능 범위다.
- 보완: Claude는 데이터 형식·좌표계·단위·결측값·출처를 제공하고, Codex는 이를 읽는 어댑터와 건설·수요 규칙을 구현한다. 데이터가 지도에 표시되는 것과 엔진에 적용되는 것을 구분해 완료 기준을 정한다.

## 4. 건설·경제 구현 전 설계 과제

아래는 기존 기능의 버그가 아니라 미구현 또는 설계가 필요한 항목이다.

### A-01. 수요 지점과 실제 역 분리

현재 엔진은 수요 지점을 역으로 사용한다. 자유로운 역 건설, 역세권, 도보 접근·환승을 구현하려면 수요 지점과 교통 시설을 분리해야 한다.

### A-02. 건설 상태와 회계 분리

계획 → 착공 → 공사 중 → 개통 상태를 정의한다. 비용 지출 시점, 취소·철거·환불 규칙, 건설 중 운행 가능 여부를 명시한다. 지도 객체의 표시 여부만으로 건설·회계 상태를 판단하지 않도록 한다.

### A-03. 경제 모델의 단위와 축척 확정

현재 승객 발생량과 차량 정원은 화면 표현용으로 축소되어 있다. 실제 요금·운영비를 그대로 결합하면 경제 균형이 맞지 않는다. 승객 한 명이 나타내는 규모, 시뮬레이션 시간, 차량 용량, 비용의 단위를 먼저 통일해야 한다.

참고: [engine README](../engine/README.md)의 현재 제약 설명. 자금과 건설비가 없는 것은 문서에 명시된 미구현 범위다.

### A-04. 저장·재현·회귀 테스트 기반

- 저장 형식 버전과 이전 버전 변환 규칙
- 고정 난수 시드에 따른 재현 가능한 실행
- 배속·프레임 간격 변화에 따른 결과 일치 검사
- 시간대 변경, 환승, 노선 삭제, 동일 지점 수요의 회귀 테스트
- 향후 건설비·운영비·환불·결산의 회계 검증

## 5. 검증 결과와 한계

실행한 기존 검증은 모두 통과했다.

- 엔진 테스트 3개 파일: bathymetry, OD demand, spatial index
- 품질 평가 테스트
- `example-radial`, `example-corridor`, `tokyo` 팩의 캐시 없는 검증

실행 명령:

```powershell
node --test transitline/engine/test/*.test.mjs
node transitline/scripts/test-quality-rubric.mjs
node transitline/scripts/validate-pack.mjs transitline/packs/example-radial --no-cache
node transitline/scripts/validate-pack.mjs transitline/packs/example-corridor --no-cache
node transitline/scripts/validate-pack.mjs transitline/packs/tokyo --no-cache
```

별도의 메모리 내 재현 사례로 열차 시간 처리, 달력 드리프트, 운행 중단 환승 경로 선택, 대기 포기, 노선 삭제 후 위치, 동일 지점 수요 예외를 확인했다. 재현 코드를 영구 테스트 파일로 추가한 상태는 아니다.

기존 테스트가 통과한다는 사실은 위 문제가 없다는 뜻이 아니다. 현재 테스트에 핵심 운행 시나리오 검사가 빠져 있다. 브라우저 전체 시나리오, 실제 HTTP 경로 접근 및 XSS 실행, 데이터 전체의 영향 규모는 추가 검증 대상으로 남는다.

검토 과정에서 기존 소스는 수정하지 않았다. 이 문서는 검토 결과를 기록한 것이며, 구현 완료 보고서가 아니다.
